# 排行榜與後台查詢摘要（0.16.34）

## 榜單與排名規則

新增 `sf_leaderboard_top100`。人生／自由模式各有超額報酬、融資、單筆獲利、輪迴次數四榜，**每個模式／分類最多 100 筆，整張表最多 800 筆**。前三榜每人一筆，保存雲端成績 ID `sf_runs.id`；輪迴榜每人一筆，保存該模式完成次數，沒有單輪成績 ID。不刪除 `sf_runs`、`sf_life_completions` 或舊 `sf_best_scores`。

- 原有效版次、現股／融資、可見成績、未停用玩家與已設定暱稱的資格不變。
- 超額報酬榜只收錄 `won`，以資產排名；融資榜以累計實借金額，單筆獲利榜以已實現淨利排名，後兩者須大於零、不限勝負。
- 前三榜同指標時依單筆獲利（空值當 0）降冪、交易次數升冪、上傳時間升冪、成績 ID 升冪；玩家最佳與全榜使用相同順序。
- 輪迴榜按完成次數降冪、最後完成時間升冪、玩家 ID 升冪。完成包含正常結算、提前結算及已驗證破產，與是否贏過大盤分開。

一般榜單從摘要讀取，JOIN 玩家與成績皆以主鍵取得顯示資料；`ROW_NUMBER()` 僅排列最多 100 筆的分區，不對完整歷史重新排名。公開快取仍為 30 秒，不混入個人身分；取得榜單後以玩家 ID 標記本人。榜外 `entry=null`，顯示「你還沒上榜，再加把勁吧！」，不再查完整榜外名次。舊 `/v1/rank` 也改為只回榜內本人。

結算不讀公開快取，只取得本輪模式的四榜。前三榜必須以**本次雲端成績 ID**比對，不能因該玩家另一輪在榜上就算本輪上榜。輪迴榜本來是玩家累計，另依本次有效完成增加判斷通知。寫入前的本人榜單資料保存在 `board_before`，搭配原持久化回條維持首次／刷新通知與重試去重。

## 寫入時維護與完成計數

Migration 0027 新增 `sf_players.life_completed_count`、`free_completed_count` 及兩模式最後完成時間；一次回填既有完成紀錄。沒有完成紀錄的玩家維持預設 0，避免回填時更新所有玩家。

SQLite `AFTER INSERT` Trigger 隨原寫入交易執行：

1. 成績真正新增時，只檢查新成績與該模式榜單，較佳才更新；新玩家不及第 100 名時不寫榜單。不逐一改寫名次欄位。
2. 完成紀錄真正新增時，更新對應模式計數及輪迴榜。`INSERT OR IGNORE` 遇到同 Session 不觸發累計，因此完成 API、成績 API 的先後、重試與並行都只計一次。
3. 註銷／恢復成績、停用／恢復玩家、資格改變、刪除成績或完成紀錄時，重新補位。這類維護允許查歷史，平常讀榜與一般新增不重排全部歷史。

後台列表直接讀玩家完成計數；點次數明細時才查逐筆完成紀錄。上傳次數、最長遊玩時長仍從該玩家的原紀錄取得，並未另加全站統計表。上方四項統計冷快取時仍須原統計查詢，本次未改成 Trigger 總計。

Session 的模式與完成紀錄的歸屬／時間視為不可變資料；現有 API 不支援修改這些欄位。若日後增加搬移或編輯功能，需同步新增維護邏輯。改變遊戲版次、相容版本或排名資格時，必須新增 Migration 更新 `sf_leaderboard_editions` 並重建榜單，不能只改 JavaScript 常數。生成工具是 `backend/tools/leaderboard-schema.mjs`；歷史 Migration 不修改。

## 後台操作與暫存

新介面使用經管理員驗證的 `GET /admin/api/runs/all`、`GET /admin/api/players/all`，每次完整查詢各執行一個列表 SQL，回傳全部管理欄位，不包含 Token、hash 或 Session 憑證。條件不傳入這兩個 API。舊分頁與 `/export` API 保留相容，舊匯出 API 的 10,000 筆限制不影響新介面。

- 首次切到列表自動查詢全部資料；之後切回使用已取得的資料。按「查詢」重新取得全量資料，恢復未篩選的列表。
- 修改條件或排列不會立刻套用，須按「篩選」。清除條件、分頁及排序都在目前頁面記憶體內處理。
- Excel 位於查詢右側，匯出**已套用條件的全部結果**，不只目前 50 筆，也不重新查 API。尚未按篩選的新條件不影響匯出。
- 同一登入頁面重複按查詢，30 秒內共用原結果；過期後也不自動重新讀取，直到再按查詢或重新整理。切頁、篩選及匯出可繼續使用較早的完整資料。
- 上方統計維持 60 秒快取；「重新整理」略過列表與統計快取。登入者列顯示簡短提示，列表另顯示查詢時間。
- 登出清除記憶體，不存入 localStorage。註銷／恢復成功會同步目前列表的狀態；其他管理員的修改需再查詢才能看到。

完整載入會增加單次回應與瀏覽器記憶體用量；資料量很大時可再考慮專用下載或漸進載入。本次依需求一次取得全部，不偷偷截斷資料。遊戲本機存檔、交易、計分與結算規則未更動。

## 本機驗證與讀寫代價

隔離的 Miniflare／workerd D1 模擬資料，使用 API 的實際 SQL；未連正式 D1。每個樣本每玩家 4 輪，單一人生模式榜回傳 100 名，對照舊排名結果完全相同。

| 每組歷史成績 | 超額報酬榜：舊 → 新 rows_read | 融資／單筆獲利榜：舊 → 新 | 輪迴榜：舊 → 新 |
| --- | --- | --- | --- |
| 600 | 3,707 → 502 | 3,703 → 503 | 2,952 → 403 |
| 6,000 | 36,107 → 502 | 36,103 → 503 | 28,602 → 403 |

回傳 100 筆不等於計費 100 列；索引、主鍵關聯與排序皆有讀取成本。`EXPLAIN QUERY PLAN` 顯示使用 `sf_top100_order(mode,category,…)` 與玩家／成績主鍵，歷史增加十倍後這組讀榜成本維持固定。一次取得所有模式／分類的成本是多個分區加總，不能把單榜數字當成整個 API 的費用。正式環境仍須觀察實際 `meta.rows_read`、`rows_written`、快取命中及 P50/P99；本機耗時不能當正式延遲。

新增維護將部分成本移至上傳：此樣本單筆成績基礎寫入 7 列，未入榜 8 列，三榜更新的較佳成績 20 列；完成紀錄由基礎 3 列變為 7 列，重複完成仍寫入 0 列。對應維護讀取分別約 713、1,036、221 列，在兩組歷史大小相同。這是特定入榜狀態的測量，不是所有案例的固定費用；首次入榜、擠出他人、管理補位及 Migration 另有成本。

已驗證原排名對照、同分第 100 名邊界、雙模式、本人標記、目前成績 ID、重送與並行、歷史回填、註銷／恢復／刪除補位、管理員驗證及 Excel。瀏覽器以 125 位玩家／100 筆成績確認：翻頁、篩選、排序與匯出沒有新增資料 API 請求；實際 Excel 匯出已套用的 32 位玩家，未套用的新條件不影響結果。

## 發布順序與回復

發布前取得正式 D1 完整備份與 Worker 版本，在備份副本驗證 Migration 0027、筆數、計數、各榜成員與 `PRAGMA foreign_key_check`。一次性回填會掃描歷史並產生寫入，應另外觀察遷移費用。正式 v0.16.34 已依此流程完成備份、回填與部署，驗證八個榜單與原始歷史資料一致，完成計數及外鍵檢查均通過。

先套用新增式 Migration，再部署 Worker，驗證後發布前端。0027 不移除原欄位，舊 Worker 仍可運作；Trigger 可維持過渡期間新增資料的計數與榜單。不能先上新版 Worker 到沒有 0027 的 schema。

回復應優先切回上一版 Worker／前端並保留新增表欄位與 Trigger，舊版讀取路徑仍可使用原始歷史；保留 Migration 狀態，不重新執行同一 Migration。若 Trigger 本身有問題，需在維護窗口修正並從原始歷史重建摘要。不要為回復而用舊備份覆蓋發布後的新玩家與成績。
